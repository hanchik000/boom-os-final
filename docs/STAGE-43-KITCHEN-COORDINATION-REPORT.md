# Stage 43 — завершение Kitchen Flow: «подать вместе», пределы по категориям, напоминания

Этап закрывает три пункта, которые Stage 42 честно оставил в «известных ограничениях».
Изменения — только в таблицах самой кухни; Order Core, Menu Engine, Inventory, оплаты и финансы
не затронуты (миграция меняет только `kds_item_tasks` и `kitchen_thresholds`).

---

## 1. «Подать вместе» стало ограничением планирования, а не только сообщением

**Было:** официант отправлял быструю команду «Подать вместе», кухня видела её как текст. Бар
наливал колу через минуту, стейк готовился 20 минут — напиток стоял под лампой.

**Стало:** та же самая команда (новых полей у заказа нет — объявление по-прежнему живёт в
`kitchen_comments`) помечает все задачи заказа и пересчитывает их темп:

* связующий момент — **самый поздний** прогноз среди позиций заказа: решает самый медленный цех;
* остальным цехам сервер говорит **начинать позже**: `forecast_start_at = ориентир − своё время`;
* время старта **никогда не уходит в прошлое** — позиция, которая не успевает, начинается сейчас;
* позиция, которая уже в работе, не перепланируется — она в сковороде;
* собственная оценка станции (`forecast_ready_at`) остаётся как была, общий ориентир пишется в
  **отдельную** колонку `coordinated_ready_at`: план и оценка никогда не подменяют друг друга.

Темп **советует**, а не запрещает: повар может начать раньше, сервер не блокирует станцию.
Экран станции пишет «Подать вместе со всем заказом — начинать в 14:32, отдать в 14:52», выдача
показывает «Официант просил подать вместе — ориентир 14:52».

## 2. Пределы задержки по категориям блюд

`kitchen_thresholds.category_id` существовал со Stage 42, но им нельзя было пользоваться. Теперь:

* предел настраивается на **филиал**, **цех** или **категорию блюд**;
* побеждает самая точная настройка: цех+категория → категория → цех → филиал → встроенный дефолт;
* проход по задержкам знает категорию каждой задачи (join на `menu_items`), поэтому для стейка и
  для колы применяются **разные** пределы;
* категория из другого филиала отклоняется (`CATEGORY_NOT_IN_BRANCH`);
* в интерфейсе менеджера появился выбор области и строка «Уже настроено: …», чтобы видеть, где что
  задано.

## 3. Напоминания об эскалации, которые действительно повторяются

`escalate_minutes` хранился, но ничего не делал. Теперь критическая задержка, которую никто не
закрыл, напоминает о себе раундами:

* раунд = `floor(минут сверх критического предела / escalate_minutes)`;
* уведомление раунда идемпотентно (`dedupe_key = escalate:<task>:<round>` + колонка
  `escalation_round`): обновление экрана сто раз не создаёт сто напоминаний;
* каждый раунд уходит менеджеру филиала с severity CRITICAL и текстом «заказ всё ещё не готов —
  задержка критическая уже N мин»;
* `escalate_minutes = 0` выключает напоминания, а не делит на ноль;
* готовая позиция перестаёт напоминать о себе.

## 4. Найденный и исправленный дефект

**Пороги принимались в значениях, которые колонка не может сохранить.** `warning/late/critical`
хранятся как `DECIMAL(5,2)`, а валидация проверяла только «больше нуля». Значение 0.004
сохранялось как **0.00**, то есть «опоздание с первой секунды» — ровно та бессмыслица, которую
проверка должна была не пустить. Теперь предел принимается только в пределах 0.1…5 и не более двух
знаков после запятой, то есть ровно в том виде, в каком его может сохранить база.

Дефекты в тестах (не в продукте), исправленные по ходу: сравнение общего ориентира по двум разным
чтениям очереди (каждое чтение законно обновляет прогноз — сравнивать нужно в одном снимке),
сравнение денежной строки `211.2` и `211.20` вместо числа, и ожидание эскалации за секунды там, где
`escalate_minutes` измеряется в минутах (сьюита теперь действительно их выжидает).
